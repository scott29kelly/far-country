## Protocol

1. Establish a clean baseline: `npm run battery` with :5173 up. Must be 18/18
   PASS. Anything else and the mutation run is void.
2. Apply exactly ONE mutation to engine source (never to a probe).
3. Run the target member. Record its verdict and the failing check IDs.
4. Run the remaining CPU members (`npm run battery -- --cpu`) to record
   cross-coverage — which OTHER members noticed. Live members are re-run only
   where a live effect is plausible, because each costs a browser boot.
5. `git checkout --` the mutated file. Confirm the target member is PASS again
   before the next mutation, so no mutation leaks into the next.

Rules of scoring:

- **CAUGHT** — the target member FAILS, on the predicted check ID.
- **CAUGHT, WRONG CHECK** — the target member FAILS but a different check
  fires. The instrument works; the prediction was wrong. Both get recorded.
- **BLIND** — the target member PASSES. A blind spot, and the reason it is
  blind goes in DEFECTS.md as a new entry.
- **UNMEASURED** — exit 2. Never counted as a pass (check.ts three-verdict
  contract).

## The three blind members

**probe-mousesteer (FC-0021)** — inverting the pitch sign in FlyCamera.ts:545
flipped the measured deltas (`dPitchTop +1.0191 → -1.1796`,
`dPitchBottom -1.1796 → +1.1689`) and the probe still printed ALL PASS. All
three steer checks assert magnitude and RELATIVE opposition only: right-edge
is `Math.abs(dYawR) > 0.05`; left-edge asserts the opposite sign *to the right
hold*; pitch asserts top and bottom oppose *each other*. Invert both yaw
signs, both pitch signs, or both axes and the probe stays green. Its own
header claims "pitch must ease upward" — prose asserting an absolute the code
never checks.

**probe-entitypick (FC-0022)** — renaming the first foundation gem to `ZZTMP`
left the battery fully green, and A2 PASSED while printing
`first=Foundation · ZZTMP`. The check is named "twelve gems in ESV order" but
its third clause is
`gemLabelOrder.every((l, i) => l === 'Foundation · ' + FOUNDATION_GEMS[i].name)`
— it compares the labels against the very table the mutation edited. Both
sides move together. Nothing in the probe knows the ESV order.

**probe-rimfalls (FC-0023)** — the severe one. #18 (`CLUSTER_M` 260 → 130)
produced output byte-identical to baseline, which is why it is scored void
rather than blind: a mutation that changes no behaviour tests nothing. #18b
(`MAX_SITES` 4 → 2) also changed nothing, which is impossible if the probe
reads that constant. Cause, at probe-rimfalls.ts:94-97 and :115: the probe
declares its OWN `MAX_SITES = 4` and `CLUSTER_M = 260` under the comment
"exact mirrors of RimFalls.ts constants", then runs an "exact replay of
findRimFallSites" inside `page.evaluate`. It never calls the shipped scanner.
#18c settles it: `findRimFallSites()` gutted to `return []` — the shipped
scanner emits nothing, every waterfall disappears from the world — and the
probe still reports "3 emergent site(s)" with R1/R2/R3 all PASS.

# Cross-coverage follow-up: gamepad-live vs a zeroed deadzone
# (pre-registered 2026-08-27, before any run)

Debt from #14 above: the deadzone mutation was scored against the CPU member
only; whether the LIVE member also notices was left untested.

Mutation: `src/core/GamepadInput.ts` `PAD_DEADZONE` 0.15 → 0. Same literal as
run #14, where CPU probe-gamepad FAILED A and C2.

## Prediction

**gamepad-live PASSES every check — BLIND.** Reason, from reading, not
running: the live probe's fake pad only ever presents axes at exactly 0 or ±1
(L3 `[0,-1,0,0]`, L4 `[0,0,1,0]`, idle `[0,0,0,0]`). `shapeStick()` is
deadzone-invariant at both magnitudes: at mag 0 it returns zero under any
deadzone; at mag 1, `t = (1 - dz)/(1 - dz) = 1` for every dz < 1, so the
shaped output is identical. The deadzone exists for PARTIAL deflections —
resting-pad drift (CPU check A, mag 0.14) and analog fractions (C2, mag 0.5)
— and the live probe never presents one.

FC-0024 differencing plan: the live probe's output is predicted byte-identical
to baseline, which would score as void UNLESS the mutation is independently
shown to change behaviour. It is: CPU probe-gamepad will be run inside the
same mutation window and is predicted to FAIL A and C2, as in run #14. That
makes an unchanged live output a genuine blind spot, not a no-op.

Known flake guard: L9 is timing-flaky (DEFECTS.md FC-0019 addendum). A red L9
in any run here is re-run before being read as signal; it is unrelated to the
deadzone path.

If the prediction holds, the blind spot gets a DEFECTS.md entry (next free:
FC-0025) and the fix is a new live check: present drift-level axes
(e.g. `[0.1, 0.1, 0.1, 0.1]`, mag 0.14 per axis pair) and assert the camera
pose and yaw hold exactly still — the live analogue of CPU check A. Verified
both ways: green on correct code, red with the deadzone zeroed.
